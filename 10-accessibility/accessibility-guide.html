Accessibility Guide

This guide defines every accessibility requirement, pattern, and code standard for the SHUSMA luxury fashion ecommerce platform. It ensures our digital experience is inclusive, perceivable, operable, and robust for every customer — regardless of ability, device, or language preference.

01. Color Accessibility

Color is central to the SHUSMA brand identity, but it must never be the sole means of conveying information. WCAG 2.1 Success Criterion 1.4.3 requires a minimum contrast ratio of 4.5:1 for normal text (below 18px regular or 14px bold) and 3:1 for large text (18px+ regular or 14px+ bold) against its background. WCAG 2.1 SC 1.4.11 additionally requires 3:1 contrast for non-text UI components and graphical objects. Our luxury gold palette demands careful pairing because several combinations fall below these thresholds and must be strictly avoided in production code. Every design decision involving color must reference this section to verify compliance before implementation.

Critical Brand Rule: NEVER use gold #C9A961 as text on light backgrounds (cream, white, or light gold). The contrast ratio is only 2.1:1 — well below the 4.5:1 AA minimum. Gold text must only appear on dark backgrounds (#1A1A1A or #5D4E37). For text on light backgrounds, always use brown #5D4E37 (8.6:1 on cream) or dark #1A1A1A (16.2:1 on cream).

Based on the contrast analysis above, the following pairings are approved for production use.   • Headings on light pages: Dark #1A1A1A on Cream #FAF8F5 (16.2:1) — maximum readability for all heading levels
  • Gold text on dark sections: Gold #C9A961 on Dark #1A1A1A (7.1:1) — hero banners, footers, dark-themed pages

Error states, success confirmations, required field markers, and stock availability indicators must all include non-color cues such as text labels, icons, or pattern indicators alongside any color coding used in the interface.

02. Typography Accessibility

Typography in the SHUSMA digital experience must balance the brand's luxury aesthetic with the functional requirements of WCAG 2.1 Success Criteria 1.4.4 (Resize Text), 1.4.8 (Visual Presentation), and 1.4.12 (Text Spacing). Every customer must be able to read product descriptions, pricing, and navigation labels without strain, including users with low vision who rely on browser zoom or custom font sizes. Our type system uses two families — Playfair Display for editorial headings and Inter for body and UI text — both selected for their excellent legibility at screen resolutions and their comprehensive support for Latin, Arabic, and extended character sets required by our multilingual audience.

Minimum Font Sizes

The base body font size for the SHUSMA website must be set to 16px (or 1rem) as the default. This is the minimum acceptable size for paragraph text, product descriptions, form labels, and any content that users need to read comfortably. The absolute minimum font size anywhere on the site is 12px, and this is reserved exclusively for captions, legal disclaimers, and metadata such as “SKU: SH-2024-AB12” beneath a product title. Even at 12px, the text must pass the 4.5:1 contrast ratio requirement against its background. Navigation items, button labels, and interactive element text must never fall below 14px to ensure readability across devices and viewport sizes.

Thin Weight Restriction: Never use font-weight 300 (thin/light) at sizes below 14px. Thin weights below this threshold fail to maintain sufficient stroke contrast against backgrounds, especially on mobile devices with varying pixel densities and subpixel rendering differences. At 14px and above, weight 300 is permitted for decorative subheadings only, never for essential UI text, labels, or data values.

Line Height and Spacing

All body text must use a minimum line-height of 1.5 (150% of the font size). For headings, a line-height of 1.2 is acceptable since the larger text provides inherent line spacing. Paragraph spacing must be at least 1.5em between consecutive blocks of text, and letter-spacing should remain at the font's default value for body copy. The maximum line length for readable paragraphs must not exceed 70ch (approximately 70 characters). Beyond this width, readers lose their place when moving to the next line, causing fatigue and reduced comprehension. Set max-width: 70ch on all content containers that hold prose text, including product descriptions, blog posts, and FAQ answers.

WCAG 1.4.12 requires that when users override text spacing (line height to 1.5, paragraph spacing to 2em, letter spacing to 0.12em, word spacing to 0.16em), no content is lost or truncated. Test this by applying these overrides in your browser's developer tools and verifying that all product cards, modals, and navigation menus reflow without clipping. The SHUSMA layout must use flexible containers and relative units (rem, em, ch) rather than fixed pixel heights to accommodate these overrides gracefully.

Responsive Type Scale

Use a modular type scale that increases proportionally across breakpoints. The recommended scale for SHUSMA is: body 16px/1rem, small 14px/0.875rem, caption 12px/0.75rem, large 18px/1.125rem, h3 20px/1.25rem, h2 24px/1.5rem, h1 32px/2rem on desktop, scaling to 40px/2.5rem for hero headlines. Always use rem units so the entire scale respects the user's browser font-size setting and zoom level. Avoid px for font-size declarations throughout the CSS codebase.

03. Touch Targets

WCAG 2.1 Success Criterion 2.5.5 (Target Size) requires that the touch target for any pointer input is at least 44 by 44 CSS pixels, with exceptions only when an equivalent link with a sufficient target size is available on the same page. For a luxury ecommerce platform like SHUSMA, this requirement directly impacts how we design product cards, navigation links, size selectors, quantity controls, and every button from “Add to Cart” to “Wishlist.” Inadequate touch targets cause frustration, mis-taps, and abandoned purchases, particularly for users with motor impairments, those using touch devices with precision challenges such as gloves or tremors, and anyone navigating on small mobile screens while multitasking.

Minimum Dimensions and Spacing

Every interactive element — buttons, links, checkboxes, radio buttons, dropdown triggers, icon buttons, and product card click areas — must measure at least 44px × 44px. This dimension applies to the visible, clickable area, not the visual icon or text label within it. For example, a wishlist heart icon may visually render at 20px, but its tap area must be padded to at least 44px in each direction. When tappable items are placed adjacent to one another, maintain a minimum of 8px spacing between the edges of their touch targets to prevent accidental activation of a neighboring control during imprecise taps.

Product Card Tap Area

On collection pages and search results, the entire product card must be tappable to navigate to the product detail page. The card itself should be at least 160px wide with no internal interactive elements that could conflict with the card's tap target. If a quick-add button or wishlist icon is placed inside the card, it must have its own distinct 44px target and be positioned with enough visual separation that users can reliably tap either the card or the embedded control. Use padding or explicit min-height values on the card to ensure the touch area extends fully, and test with actual finger input on physical devices rather than relying solely on mouse clicks during development and QA.

Add-to-Cart Button Sizing for Mobile

The “Add to Cart” button is the most critical touch target on any product detail page. On mobile viewports, this button must span the full width of the content area (minus standard padding) and have a minimum height of 48px. The recommended height is 52px to provide a comfortable, forgiving tap area that accommodates thumb reach. The button's font size must be at least 16px to prevent iOS Safari from triggering automatic zoom on focus, which disrupts the shopping experience and requires users to zoom back out manually. Secondary actions like “Add to Wishlist” must be at least 44px tall and visually distinct from the primary CTA. Quantity increment and decrement controls must each meet the 44px minimum and include clear plus/minus labels alongside any icon.

04. Screen Readers

Screen reader support is essential for SHUSMA's ecommerce platform because blind and low-vision customers must be able to browse collections, examine product details, select sizes and colors, add items to their cart, and complete checkout independently. WCAG 2.1 Success Criteria 1.1.1 (Non-text Content), 1.3.1 (Info and Relationships), 4.1.2 (Name, Role, Value), and 4.1.3 (Status Messages) all govern how we structure HTML and ARIA markup to ensure assistive technologies can parse and communicate every interface element accurately. A luxury fashion site is inherently visual, which makes semantic markup and descriptive alternatives even more critical for creating an equitable shopping experience.

ARIA Labels for Brand Icons

Decorative icons that convey no information must use aria-hidden="true" to prevent screen readers from announcing meaningless content. Functional icons — such as the search icon, cart icon, account icon, and close button — must have accessible names via aria-label, aria-labelledby, or a visually hidden text node. For example, a cart icon in the header must include aria-label="Shopping cart, 3 items" that dynamically updates when items are added or removed via JavaScript. Brand-specific icons that serve as links (like a SHUSMA monogram linking to the homepage) must use aria-label="SHUSMA - Home" rather than relying solely on the logo image's alt text, because the link's purpose must be clear even if the image fails to load.

Product Image Alt Text Patterns

Product images require descriptive alt text that communicates what the image shows and its relevance to the purchase decision. A standard product photo on a detail page should follow the pattern: [Brand] [Product Name] in [Color], [Descriptive detail]. For example: alt="SHUSMA Silk Blazer in Midnight Blue, front view showing notch lapel and single-button closure". Thumbnail images in carousels can use shorter descriptions: alt="Silk Blazer - side view". When the same product is shown in multiple angles, each angle should be distinctly identified. Grouped product images (e.g., a model wearing the full outfit) should describe the context: alt="Model wearing the SHUSMA Silk Blazer paired with Tailored Trousers at a gallery event".

Skip Navigation and Landmark Regions

Every page must include a skip navigation link as the first focusable element, allowing keyboard users to bypass the header and navigation and jump directly to the main content area. The SHUSMA site must use semantic HTML5 landmark elements — <header>, <nav>, <main>, <aside>, and <footer> — to create a predictable page structure that screen readers can announce and navigate between. Each landmark should have a unique accessible name where multiple instances exist (e.g., <nav aria-label="Main navigation"> vs. <nav aria-label="Footer navigation">). The search region should use <search aria-label="Product search"> per the HTML5.2 specification.

Live Regions for Cart Updates

When a user adds an item to the cart, changes quantity, or removes an item, the cart count and subtotal must update without requiring a page reload. These dynamic changes must be communicated to screen reader users via ARIA live regions. Use aria-live="polite" on the cart summary container so that updates are announced after the current speech output finishes. For critical alerts (e.g., “Item added to cart” confirmation or “Out of stock” error), use aria-live="assertive" to interrupt immediately. Apply role="status" to toast notifications that appear after actions like adding to wishlist or applying a promo code.

05. Keyboard Navigation

Full keyboard operability is a foundational WCAG 2.1 requirement (SC 2.1.1, 2.1.2, 2.4.3, 2.4.7) and is particularly critical for an ecommerce platform where every interaction — from browsing products to entering payment details — must be achievable without a mouse. Keyboard-only users include people with motor impairments, screen reader users who navigate by tab and arrow keys, power users who prefer keyboard shortcuts for efficiency, and developers debugging the interface. The SHUSMA site must provide a visible, high-contrast focus indicator on every interactive element, a logical tab order that follows the visual layout, and keyboard equivalents for all mouse-dependent interactions such as dropdown menus, carousels, product image zoom, and modal dialogs.

Gold Focus Outline

The SHUSMA focus indicator uses a 3px solid outline in gold #C9A961, which provides a contrast ratio of 7.1:1 against the dark #1A1A1A header and footer backgrounds. Against the cream #FAF8F5 background, the gold outline alone provides only 2.1:1 contrast, which falls below the 3:1 non-text contrast requirement (SC 1.4.11). To compensate, we add a 2px dark #1A1A1A box-shadow offset behind the gold outline, ensuring the focus state is clearly perceivable on all backgrounds including the cream primary background. This dual-layer approach meets WCAG requirements while maintaining brand consistency. The focus indicator must use :focus-visible rather than :focus to avoid showing outlines on mouse clicks while preserving them for keyboard navigation.

Tab Order and Focus Management

The default tab order must follow the visual reading order: top to bottom, left to right (or right to left for Arabic content). Do not use tabindex values greater than 0, as they disrupt the natural tab sequence and create confusing experiences for assistive technology users. When a modal dialog opens (such as a size guide, quick-view product overlay, or promo code popup), focus must move into the modal and be trapped there until the user closes it. When the modal closes, focus must return to the element that triggered it. Use the inert attribute on the background content to prevent keyboard access while a modal is open, or manage focus programmatically with focus() calls. The Escape key must always close any open modal, dropdown, or expanded menu.

Keyboard Shortcuts

The SHUSMA site must not implement custom single-key keyboard shortcuts (WCAG SC 2.1.4), as these can conflict with assistive technology commands. If any keyboard shortcuts are provided, they must use modifier keys (e.g., Ctrl+K for search, Escape to close) and must be documented in an accessible help panel reachable from the footer. The search field should activate with / only when no input or textarea is currently focused. Carousel widgets must support arrow keys for navigating between slides, and product image galleries must allow keyboard users to cycle through thumbnails with arrow keys and open zoom views with Enter or Space.

CSS — Focus Styles 
/* SHUSMA Focus Indicator System */

/* Remove default outline globally */
*:focus {
  outline: none;
}

/* Visible focus for keyboard navigation only */
*:focus-visible {
  outline: 3px solid #C9A961;
  outline-offset: 2px;
  /* Dark shadow ensures visibility on cream background */
  box-shadow: 0 0 0 2px #1A1A1A;
}

/* On dark backgrounds, shadow not needed */
.dark-section *:focus-visible {
  box-shadow: none;
  outline-offset: 3px;
}

/* Skip link focus state */
.skip-link:focus {
  top: 0;
  outline: 3px solid #FAF8F5;
  outline-offset: 2px;
}

/* No focus ring on mouse click */
.product-card:focus:not(:focus-visible) {
  outline: none;
  box-shadow: none;
}

/* Modal focus trap indicator */
.modal[open] *:focus-visible {
  outline: 3px solid #C9A961;
  outline-offset: 2px;
  box-shadow: 0 0 0 2px #FAF8F5;
}

06. Motion & Animation

WCAG 2.1 Success Criterion 2.3.3 (Animation from Interactions) requires that users can disable non-essential motion triggered by their interactions. Additionally, SC 2.2.2 (Pause, Stop, Hide) requires that auto-playing content lasting more than 5 seconds can be paused or stopped. For the SHUSMA luxury fashion brand, animations such as gold shimmer effects on hero text, parallax scrolling on lookbook pages, loading spinners, and auto-advancing product carousels all fall under these requirements. Users with vestibular disorders, photosensitive epilepsy, or motion sensitivity can experience nausea, dizziness, or headaches from animated content, making these accommodations both a compliance requirement and an ethical imperative for an inclusive luxury brand.

prefers-reduced-motion Implementation

The prefers-reduced-motion: reduce media query must be respected at the CSS level to disable or significantly simplify all non-essential animations. When this preference is active, the SHUSMA site must: instantly show all content that would normally animate in (no fade-ins, slide-ins, or scale transitions), remove the gold shimmer effect from hero headlines and decorative text, disable parallax scrolling on lookbook and campaign pages, replace carousel auto-advance with manual-only navigation, and eliminate hover-triggered micro-animations on product cards. Essential functional transitions like focus indicator appearance should remain but can be reduced to an instant state change. JavaScript-driven animations must also check this preference using window.matchMedia('(prefers-reduced-motion: reduce)') and skip or simplify animation sequences accordingly.

Loading Spinner Alternatives

Loading spinners present accessibility challenges because screen readers cannot perceive rotating visual elements, and some users find continuous spinning distracting or harmful. The SHUSMA site must supplement or replace visual spinners with accessible text indicators. When a page section or product image is loading, include a visually hidden text node: <div role="status" aria-live="polite" class="visually-hidden">Loading product details...</div>. For skeleton screens (preferred over spinners for modern luxury aesthetics), add aria-busy="true" on the container and use role="status" for announcements. Progress bars for operations like checkout processing must include both a visual bar and an accessible text percentage or step description.

Carousel Auto-Play Controls

Any carousel that auto-advances (e.g., hero banner rotation, editorial lookbook slider) must provide visible pause, play, previous, and next controls. The auto-advance must pause when the user hovers over or focuses on the carousel, and must not resume automatically after manual interaction — the user must explicitly press play to restart. The carousel must expose the current slide number and total slide count accessibly, using aria-roledescription="carousel" on the container and aria-roledescription="slide" with aria-label="Slide X of Y" on each slide. When auto-play is disabled via prefers-reduced-motion: reduce, the carousel must default to a static state.

JavaScript — Motion Preference Check 
// Check reduced motion preference in JavaScript
const prefersReducedMotion = window.matchMedia(
  '(prefers-reduced-motion: reduce)'
);

function initCarousel(element) {
  const shouldAutoPlay = !prefersReducedMotion.matches;
  const carousel = new Carousel(element, {
    autoPlay: shouldAutoPlay
  });

  // React to runtime preference changes
  prefersReducedMotion.addEventListener('change', (e) => {
    if (e.matches) {
      carousel.stopAutoPlay();
    } else {
      carousel.startAutoPlay();
    }
  });

  return carousel;
}

07. Form Accessibility

Forms are the backbone of the SHUSMA ecommerce experience — from newsletter signups and search fields to product customization and multi-step checkout. WCAG 2.1 Success Criteria 1.3.1 (Info and Relationships), 1.3.5 (Identify Input Purpose), 3.2.2 (On Input), 3.3.1 (Error Identification), 3.3.2 (Labels or Instructions), 3.3.3 (Error Suggestion), and 4.1.2 (Name, Role, Value) all apply directly to form design and implementation. Every input must have a visible, programmatically associated label; every error must be specific, actionable, and linked to its field; and the entire checkout flow must be operable by keyboard and screen reader without any ambiguity about what information is required or what went wrong during submission.

Labels and Input Association

Every form input must have an associated <label> element using the for attribute that matches the input's id. Placeholder text must never serve as the sole label for an input, because placeholders disappear when users start typing and are not reliably announced by all screen readers. If visual design requires a floating label inside the field, implement it as a positioned <label> element that moves above the input on focus or when the field has a value, maintaining its programmatic association at all times. Required fields must be indicated with the word “required” in the label text or via aria-required="true", not by color alone. The asterisk convention may be used visually but must be supplemented with screen-reader-accessible text.

Error Messages with aria-describedby

When form validation fails, error messages must be displayed adjacent to the relevant field and linked programmatically using aria-describedby. The error container's id must be referenced in the input's aria-describedby attribute, and the input must receive aria-invalid="true". Error text must be specific and actionable — instead of “Invalid email,” use “Please enter a valid email address, such as name@example.com.” Instead of “Required,” use “Please select a size before adding to cart.” Errors must be announced by screen readers via the aria-describedby association and, for dynamically displayed errors, via an aria-live="assertive" region that announces the error immediately upon form submission.

Autocomplete Attributes

WCAG SC 1.3.5 requires that inputs intended for specific types of data include appropriate autocomplete attributes. This enables browsers and password managers to autofill information accurately, which is especially valuable during checkout where users must enter shipping and billing details. Use standard HTML autocomplete tokens: autocomplete="given-name", autocomplete="family-name", autocomplete="email", autocomplete="street-address", autocomplete="cc-number", etc. The SHUSMA checkout form must support these attributes on all personal information and payment fields. For the newsletter signup in the footer, use autocomplete="email" to allow quick subscription without retyping.

Multi-Step Checkout and Color Pickers

The SHUSMA checkout flow uses a multi-step wizard pattern (Shipping → Payment → Review). Each step must function as a distinct section with its own heading, and a progress indicator must communicate the current step, total steps, and completed steps using aria-current="step" on the active step and visual plus programmatic indicators for completed steps. Users must be able to navigate back to previous steps without losing entered data. For product color selection, implement the color picker as a set of radio buttons with role="radiogroup" and aria-label on the group. Each color swatch must be an actual <input type="radio"> (visually styled as a circle) with a label that names the color (e.g., “Midnight Blue,” “Champagne Gold”), never relying on color swatches alone without text labels.

08. Image Alt Text

Images are the primary medium through which SHUSMA communicates product quality, craftsmanship, and brand aspiration. For users who cannot see these images — including blind users, users with low vision using screen magnifiers, users on slow connections who have disabled images, and search engine crawlers — alternative text is the only way to understand what is depicted. WCAG 2.1 SC 1.1.1 (Non-text Content) requires that every image that conveys meaning has a text alternative, and that purely decorative images are marked so that assistive technologies ignore them. On an ecommerce site, missing or poor alt text directly impacts sales because customers cannot make informed purchase decisions without understanding the products they are viewing.

Product Photography Alt Text Patterns

Product images on detail pages are the highest-priority alt text on the site. Each image must describe the product, its key visible features, and the angle shown. Use the pattern: [Product Name] in [Color], [view angle] showing [key detail]. For example, a main product image might read: alt="SHUSMA Hand-Stitched Leather Tote in Cognac Brown, front view showing structured silhouette, rolled top handles, and gold-tone clasp". Additional gallery images at different angles should identify the view clearly: alt="Hand-Stitched Leather Tote - interior view showing suede lining and zip pocket". Close-up detail shots should name the specific feature: alt="Detail of hand-stitched leather panel on the SHUSMA tote bag". Group shots showing multiple products must list each item.

Lifestyle and Editorial Images

Lifestyle images — such as lookbook photos, campaign imagery, and editorial content — require descriptive alt text that captures the scene, the products being worn or used, and relevant contextual information. For example: alt="Model wearing the SHUSMA Silk Blazer and Tailored Trousers standing in a sunlit gallery with abstract art in the background". If a lifestyle image conveys a brand message beyond the products shown (e.g., a campaign about sustainability), include that context: alt="Close-up of organic cotton fabric draped over a craftsman's hands, illustrating SHUSMA's commitment to sustainable artisan production". Avoid subjective language like “beautiful” or “stunning” in alt text — focus on objective, observable content.

Decorative SVGs and the SHUSMA Logo

Decorative SVGs — including ornamental dividers, background patterns, abstract gold flourishes, and geometric accents — must be marked with aria-hidden="true" and have an empty alt="" attribute if wrapped in an <img> tag. Inline SVGs used decoratively must include aria-hidden="true" and must not have <title> or <desc> elements that would cause screen readers to announce them. The SHUSMA logo, when used as a link to the homepage, must have alt="SHUSMA". When the logo appears in a non-interactive context (email footer, print receipt), it should also use alt="SHUSMA". Never leave logo alt text empty unless the logo is purely decorative.

09. Arabic RTL Support

SHUSMA serves customers across the Middle East and North Africa region, making Arabic language support a core requirement rather than an afterthought. Arabic is a right-to-left (RTL) script, which requires mirroring of the entire layout — navigation moves to the right, text alignment flips, icons that imply directionality must be mirrored, and content flows from right to left. WCAG 2.1 SC 3.1.1 (Language of Page) and SC 3.1.2 (Language of Parts) require that the language of all content is programmatically determinable, which means every Arabic page must declare lang="ar" dir="rtl" on the <html> element. Any English passages within Arabic content (brand names, product codes, prices) must be marked with lang="en" dir="ltr" so screen readers switch pronunciation and text direction correctly.

Logical CSS Properties

The SHUSMA CSS codebase must use logical properties instead of physical directional properties to support bidirectional layouts without maintaining separate stylesheets. Replace margin-left with margin-inline-start, padding-right with padding-inline-end, border-left with border-inline-start, text-align: left with text-align: start, and float: left with float: inline-start. This approach ensures that when dir="rtl" is set on the page, all layout calculations automatically flip without additional CSS. Physical properties should only be used in rare cases where a specific side must remain fixed regardless of text direction (e.g., a fixed sidebar that always appears on one side for consistency).

Mirroring Layout and Icons

The entire page layout must mirror when switching between LTR (English) and RTL (Arabic). The header navigation moves from the left to the right, the shopping cart icon moves to the left of the header, sidebar panels slide in from the right, and breadcrumb separators flip direction. Icons that imply directionality — arrow icons in carousels, chevrons in dropdowns, back/forward navigation arrows — must be mirrored using CSS transform: scaleX(-1) within RTL contexts. Product image carousels must reverse their swipe and arrow-key directions in RTL mode, and the visual order of product variant thumbnails must mirror to follow natural reading flow.

Mixed English/Arabic Content Handling

Product pages frequently mix Arabic descriptions with English brand names, prices in USD or SAR, size labels (S, M, L, XL), and material terms. Each language segment must be wrapped in the appropriate <span lang="en" dir="ltr"> or <span lang="ar" dir="rtl"> element. Numbers and prices should use dir="ltr" even within Arabic text, as numerals always read left-to-right. The SHUSMA brand name should always appear in its Latin form within English-marked spans. Form inputs must handle RTL text entry correctly, including right-aligned placeholder text, RTL cursor movement, and proper text selection behavior for bilingual users.
